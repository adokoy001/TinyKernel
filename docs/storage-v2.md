# TaneFS v2 — 更新記録と障害後の復旧

更新: 2026 10 04 / Tane OS 0.9

TaneFS v2は、1ファイルの変更後の内容とメタデータを、チェックサム付きのredo journalへ先に保存します。commitを記録してから本来の場所へ反映するため、途中で停止した更新を次回のマウント時に再実行できます。シェルとring 3のファイルsyscallは、同じstorage入口、MAC、変更番号を使います。

これは固定容量の小さなファイルシステムです。最大32ファイル、1ファイル4096バイト、名前は1〜47バイトの英数字・`.`・`_`・`-`で、ディレクトリや可変長のextentはありません。Admin/Userのファイル数上限は、それぞれ24件・8件です。

## ディスクを使う

`sh run.sh`は、初回に`build/disk.img`という1 MiBのIDEデータディスクを用意します。新しいディスクではadminのシェルで`file format`します。formatは既存データをすべて消す操作です。

```text
file format
file write notes "before"
file append notes " after"
file read notes
file list
disk
```

`file format`で作るのはv2です。旧版v1のディスクも読めますが、書き込みは拒否します。v1を起動しただけで変換したり、書き換えたりはしません。

旧ディスクをファイルとラベルを保ったままv2へ切り替えるには、adminの`file upgrade`を使います。対象ディスクには275セクター以上必要です。操作前にコピーを残す場合は、QEMUを終了してからホスト側で`build/disk.img`をコピーしてください。formatによる移行はファイルを消すため、既存ファイルを残すupgradeとは別の操作です。

名前変更、ファイルの伸縮、検査とflushも使えます。

```text
file rename notes renamed
file truncate renamed 3
file read renamed
file truncate renamed 8
file status | json
file check | json
file sync
```

renameは既存の名前へ上書きせず、ラベルと内容を保ちます。truncateは0〜4096バイトを指定し、延長分をゼロにします。`file check`は現在のドメインに読めるファイルだけを全内容のチェックサムで検査し、成功したファイル数と合計バイト数を返します。`file status`は版・readonly・マウント時のreplayの有無も返します。`file sync`はadmin専用の明示的flushです。ring 3のhandleにはseek・cursor位置からのwrite・truncateを用意し、成功した変更は同じjournalを通します。

## v1を明示的にupgradeする

```text
file status | json
file upgrade
file status | json
file check | json
```

`file upgrade`はadmin専用で、formatと同じMAC権限を使います。v2で呼ぶと変更しません。v1では、全ファイルの内容チェックサムと、マウント時のファイル表との一致を、書き込み前に検査します。壊れた内容や表、容量不足があれば書き始めません。

全ファイルの本体・表・ラベル・世代はそのままに、LBA 5の表チェックサム一覧を書いてflushし、LBA 264のcommit headerをゼロにしてflushします。旧v1のスーパーブロックはこの間そのままです。最後にv2のスーパーブロックを書いてflushし、新しい版を公開します。

最後の公開前に止まれば、ファイル本体を保ったv1として読めます。原子的な最終セクター書き込みとflushが守られる場合、公開後はv2として読み書きできます。最終スーパーブロックが途中でtearした場合はマウントを拒否します。ファイル本体を上書きしない移行ですが、任意のtear後にも必ずマウントできる保証や、自動で旧headerへ戻す修復機能はありません。upgradeのI/O失敗でも、使用中のマウントを無効化します。

## 固定配置

セクターは512バイトです。v2には最低275セクターが必要で、`run.sh`の1 MiBディスクはこの条件を満たします。ファイルのデータ位置はv1と同じです。

| LBA | 内容 |
| --- | --- |
| 0 | v2スーパーブロック。magic、版、配置、サイズ、チェックサム |
| 1〜4 | ファイル表。1件64バイト、32件 |
| 5 | ファイル表4セクターのチェックサムと、その一覧自身のチェックサム |
| 6〜7 | 予約領域 |
| 8〜263 | ファイル本体。slotごとに8セクター・4096バイト |
| 264 | commit header。対象slot、反映先、payloadチェックサム、commit印、headerチェックサム |
| 265〜272 | 変更後のファイル本体8セクター |
| 273 | 変更後の対象ファイル表1セクター |
| 274 | 変更後の表チェックサム一覧1セクター |

journalはheader 1セクターとpayload 10セクターの合計11セクターです。1回に保持する変更は1ファイル分です。ファイルのラベル、サイズ、世代、内容チェックサムも更新後の表に含めます。名前やラベルの検査に加え、表のチェックサムを確認してからマウントします。

## 1回の変更を確定する順序

1. 前のcommit headerをゼロにし、flushが完了するまで待つ。
2. 変更後のファイル本体・対象の表・表チェックサム一覧をjournalのpayloadへ書き、flushを待つ。
3. payloadを指すチェックサム付きcommit headerを書き、flushを待つ。このdurableなcommit印が更新の確定点。
4. journalから本来のファイル本体・表・チェックサム一覧へコピーし、flushを待つ。
5. commit headerをゼロにし、最後のflushを待ってから成功を返す。

commit前には本来のファイルを上書きしません。commit後の反映に失敗しても、journalを先に消しません。更新はデータと対応するメタデータをまとめて再実行できます。write・append・deleteなどの通常の変更は、この同じ順序を使います。1つのパイプラインやスクリプトの複数ファイルを、まとめてcommitする機能はありません。

すべてのファイル操作を割り込み禁止の区間で直列化します。syscallや別のtaskが、journalの途中へ別の書き込みを混ぜることはありません。その間はタイマーによる切り替えも遅れます。ATAのポーリングには上限がありますが、ディスクI/Oを非同期にする仕組みはありません。

## 起動時の復旧とエラー

マウント時には、ファイル表を使う前にjournalを調べます。

| journalの状態 | マウント時の動作 |
| --- | --- |
| headerが全ゼロ | commit済みの未反映更新はないとして、表を検査する |
| 有効なcommit headerとpayload | payload全体の内容・表・チェックサムを先に検査し、本来の場所へ再反映してflushし、headerを消してflushする |
| 途中で壊れたheader、checksum不一致、矛盾したpayload | journalを消したり部分反映したりせず、マウントを拒否する |

復旧そのものの途中で停止しても、commit headerを残している間は次の起動で再実行します。再実行は変更後の同じ8セクターと表を上書きするため、appendの文字列を二重に足す処理ではありません。破損したファイル本体は、読み取り時に全内容のチェックサムを調べ、表示や部分readで返す前に拒否します。

変更中のI/Oエラーは、成功にも自動ロールバックにも扱いません。シェルは`commit-unknown`、ring 3には`EIO`を返し、マウント中の状態を無効化します。commit印のflushが失敗した場合も、その印が実際に永続化されたかは呼び出し元から断定できません。次の起動で、ディスク上の記録を検査して復旧します。再起動せずに壊れた状態へ書き続けることはしません。

`plan`はユーザーが変更内容を先に確認するための仕組みで、journalとは役割が異なります。plan/applyの状態照合から実際の変更まで同じ保護区間で行い、他のファイルやUserのsyscallによる変更でも古いplanは失効します。

## 消去、再利用、handle

ファイル本体は更新ごとに8セクター全体を用意し、EOFより後ろをゼロにします。削除のpayloadは8セクターすべてゼロで、反映後の表から名前とラベルも除きます。slotを再利用しても、前の内容を新しいファイルの余りとして返しません。これはファイルAPIの再利用境界で、デバイスの物理消去やホスト側snapshotの削除は保証しません。

handleは名前・slot・ラベル・サイズ・世代・checksum・起動中の変更epochを固定します。名前変更や内容の変更、同名ファイルの削除と再作成で、古いhandleは新しい対象へ付け替わりません。書いたhandle自身を更新する操作を除き、古いidentityの要求は`ESTALE`です。ファイルのMACは共有のAdmin/Userドメイン単位で、Userプロセス別の所有者や秘密ディレクトリはありません。

## 保証の前提と限界

durableな512バイトセクター書き込みと、先行書き込みを永続化するflushをデバイスが正しく実装することが、旧内容またはcommit後の新内容へ復旧する前提です。ATAドライバは各barrierでFLUSH CACHEを発行して完了を待ちます。電源断後に実デバイスがこの契約を破る場合までは保証しません。

セクターの途中だけが書き換わるtearは、チェックサムと構造検査で検出できる場合にマウントを拒否します。checksumは32ビットのFNV-1aで、偶発的な破損検出用です。暗号学的な認証や敵対的な偽造防止ではなく、衝突がないという保証もありません。すべての壊れ方から自動復旧できるという意味ではありません。

formatは通常の1ファイル更新と違い、破壊的な全体操作です。最初に旧スーパーブロックを無効化してflushし、全領域を初期化してから新しいheaderを最後に保存します。途中で止まれば、ディスクは未formatのままになり得ます。旧ファイルへ戻す原子性はありません。

ホストの障害注入とQEMUでの起動は実装の挙動を検査するもので、形式証明ではありません。テスト結果、使用したイメージのSHA-256、確認範囲は`build/verification.txt`と各summaryに記録します。
